# Govtech Visualizer: Product Definition

*"Govtech Visualizer" is a working name; it will be renamed later.*

*Agreed on 2026-10-22. Companion document: `technical-details-2026-10-22.md`. Original brief: `proposal.md`.*

## Purpose

A VJ / visual performance designer built on the projectM (MilkDrop) renderer. It lets an artist browse the full MilkDrop preset library visually, combine presets with video into **scenes**, arrange scenes into a **performance**, and play that performance live on a projector or second display, with scene changes triggered over MIDI from Ableton.

The target user is a **non-technical visual artist**. Nothing should need a text editor, a terminal or editing JSON by hand.

It is the **last step in the video chain**: its output goes to a screen and nowhere else.

It starts from our fork of projectM, https://github.com/kurtvan/libprojectM-4.1.4, which is a working prototype of scenes, Syphon/video injection and MIDI scene triggers. Most of that fork's app layer will be rewritten (see the technical document).

## Scope principles

- **macOS only for now**, but avoid decisions that make other platforms impossible later (Windows/Spout, Metal).
- **Free.** Distribution, signing, notarization and packaging are out of scope for this effort.
- Start simple, but leave room for each "later" item below.

## Core concepts

| Concept | Definition |
|---|---|
| **Preset library** | A folder of `.milk` presets the user chooses (intended to be the "Cream of the Crop" pack). Indexed by the app. **Not bundled** with the app; the user supplies it to avoid licensing issues. |
| **Favourite** | A preset the user has starred. Stored in an app-level library file, available to every performance. |
| **Scene** | One visual state: a preset, an optional video source (Syphon or a video file) with its blend settings, and a MIDI trigger value. |
| **Performance** | An ordered list of scenes, saved as a JSON file. |

## Features

### 1. Preset browser
- On first launch, the user picks their preset folder. The app indexes it and can re-index on demand.
- Presets are shown in a **virtualized grid/list**. Only items on screen do any work.
- **Live mini-previews:** each visible tile shows a tiny (about 160×90) live render of the preset updating at about **1 fps**. Previews don't react to the live audio input; they run on a built-in test signal. The name shows immediately and the preview appears once the preset has compiled (about 50–500 ms per preset). A page of tiles fills in progressively; there is **no upfront wait** and no "generate all thumbnails" step.
- The last rendered frame of each preset is cached on disk so revisiting a page shows images instantly.
- A **"names only" switch** disables previews entirely.
- **Tags** are derived from folder structure: the two folder levels in Cream of the Crop (e.g. `Dancer` / `Glowsticks Mirror`) become a two-level category filter. The **author** is parsed from the filename prefix (e.g. `shifter - mandala`) as an extra search facet.
- Text search over name, tags and author.
- Presets that fail to compile or render black are flagged with a **broken placeholder**.

### 2. Favourites
- Star/unstar presets from the browser.
- Favourites filter/view in the browser for building performances quickly.
- Favourites persist across sessions and performances (app-level, not per performance).

### 3. Scenes
Each scene has:
- **Preset**: chosen from the browser. Used as-is; no preset parameter editing.
- **Video** (optional):
  - **Source type:** `syphon` (pick a Syphon server from a list of what's currently available) or `file` (choose a video file with a native file picker).
  - **Mix**: blend amount of the video into the preset (0–1).
  - **Luma gate**: brightness threshold below which video is transparent (0–1).
  - **Restart video** on scene entry (for file sources).
  - Video is blended into the preset's **warp feedback**, so the preset distorts the video rather than the video being laid on top.
- **MIDI trigger value**: the CC 20 value (0–127, unique per performance) that fires this scene (see MIDI below). Defaults to the lowest free value and stays the same when scenes are reordered.
- **Name/ID**: user-editable label.
- All per-scene values are **fixed in the scene**; none are live-controlled by MIDI.

### 4. Performances
- An **ordered, linear list of scenes**, shown sequentially in the editor.
- Add, remove, duplicate and reorder scenes.
- Any scene can be triggered at any time (out of order), not only the next one.
- Saved as **JSON files** referencing **absolute paths** to presets and videos.
- Missing files (preset or video) show a **broken placeholder** in the scene list and the browser; the app never crashes on a missing file.
- Up to **128 scenes** per performance (the range of one MIDI CC).
- **Playback is tuned for linear order.** Moving to the next scene must be instant (hard cut, no stutter). Jumping out of order may cause a brief stutter; the last frame is held rather than showing black.
- **Every scene starts fresh** when entered, including when going back to a scene that already played.

### 5. Live performance
- **One editor window** on the main display: a large preview panel taking most of the screen, with the browser, scene list and scene properties around it.
- **A separate output window**, borderless fullscreen on a chosen second display, shown during performance and rendered at **that display's native resolution**. The editor preview shows the same image.
- **Hard cuts only** between scenes (no crossfades).
- Before the first trigger the output stays black.

### 6. MIDI
- **CC 20 on one MIDI channel** triggers scenes: the CC value (0–127) selects the scene whose trigger value matches.
- No other MIDI mappings. Mix, luma etc. are not MIDI-controlled.
- Ableton (via the IAC Driver or another MIDI source) is the expected controller.
- Devices connected after launch should be picked up.
- One channel, 128 values: a performance holds at most 128 scenes, each with its own value.

### 7. Audio input
- A simple **selector listing macOS audio input devices**. The selected device drives the presets' audio reactivity.
- An input **gain** setting (replacing the fork's hard-coded 4× boost).
- The author currently routes Ableton in with Loopback. Making audio routing easy for non-technical users is a later effort.

## Explicitly out of scope (for now)

| Item | Status |
|---|---|
| Syphon **output** / sending video to other apps | Not needed; this is the last step in the chain. |
| Crossfades / transitions | Later. |
| Free-flowing / non-linear (clip-launcher style) performances | Later; the data model must not rule it out. |
| More than 128 scenes per performance | Later, if ever; would need a trigger scheme beyond one CC. |
| Preset parameter editing per scene | Later; a nice idea. |
| MIDI mapping beyond CC 20 / MIDI learn | Not planned. |
| Portable "packed" performances (bundle videos and presets) | Later; the format includes a version field to allow migration. |
| Person segmentation / masking | Removed. Do it upstream before video arrives via Syphon. |
| Windows / Spout, Metal renderer | Later; avoid blocking them. |
| Easy audio routing for non-technical users | Later. |
| Distribution, signing, notarization, licensing packaging | Later effort. |
| Bundling the preset library | Never by default; the user supplies it. |
